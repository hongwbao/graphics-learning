## 自主学习讲解

### 先有参考，再谈“画错了”

截图像不像不是唯一标准。先固定相机、几何、纹理与绘制顺序，把一个正常场景作为参考。接着只改变一个因素：相机 X 改变轮廓位置；纹理频率改变表面明暗分布；深度设置改变重叠区域。若轮廓、纹理和遮挡一起变化，先检查是不是多个输入同时动了。

本周屏幕中的物体由真实三维顶点与三角形投影而来，但执行者是浏览器中的 CPU 软件光栅器，不是 WebGL GPU。这样能显式检查每个候选片段；不将运行速度当作实时 GPU 性能。

### 连接相机、投影与采样位置

x_ndc = f x_view / d / aspect
y_ndc = f y_view / d，d = −z_view > 0

f = 1/tan(FOV/2)，FOV 是竖直视场角，aspect 是宽高比。相机先从世界位置得到观察坐标，投影才把不同深度映到二维。实验中的近裁剪限制为 d>0.1；为了简化，碰到近面的整个三角形会被跳过，因此不要把极端相机位置的缺口当作正式裁剪结果。

OpenGL 中这部分通常来自 V、P 与透视除法。本实验保留相同的几何含义，直接算屏幕坐标，避免窗口和驱动代码遮住学习目标。

### UV 不应该在透视图像里随便线性混合

u = [Σ λ_i u_i / d_i] / [Σ λ_i / d_i]

λ_i 是像素中心在屏幕三角形中的重心权重；u_i 是顶点纹理坐标，d_i 是该顶点到观察平面的正距离。v 同理。每个角点都落对，并不保证中间的 UV 正确；透视下要先按倒数深度加权，再除回权重和。

局部一张图案在斜面上被拉伸，可能是 UV、插值或采样错误；它不直接说明三维重建几何一定错了。

### 深度和绘制顺序是两套规则

本实验在每个像素保存最近候选的正距离 d。开启测试时，只保留更小的 d；关闭后，最后提交的候选覆盖前面的颜色。这里用 1/(Σ λ_i/d_i) 重建表面的观察距离，便于建立“近处更小”的直觉，不直接模拟 GPU 的非线性窗口深度。

交换绘制顺序：深度开启时应基本相同，关闭时可能翻转。同一立方体的背面也会产生候选，因此错误可能先出现在单个物体内部。边界采样不含完整 top-left 规则，少量共享边像素差异不应被误认作整体遮挡错误。

## 交互实验

软件渲染诊断台：相机 × 棋盘 × 深度

移动相机、改变棋盘频率、交换三角形顺序；每次先预测哪些位置应改变。核心代码真实处理投影后的候选片段，输入中每个 f 包含像素编号 i、距离 z 与透视插值后的 u/v。

可调输入：

- 相机 X（cameraX）：默认 0，范围 -1.5–1.5
- 相机沿 Z 移动（cameraZ）：默认 0，范围 -0.5–2
- 相机偏航角（yaw）：默认 0，范围 -15–15
- 竖直 FOV（fov）：默认 55，范围 35–85
- 棋盘格频率（frequency）：默认 8，范围 2–24
- 深度测试（depth）：默认 on；on=开启，off=关闭
- 三角形提交顺序（order）：默认 normal；normal=原顺序，reverse=逆序

### 核心代码

先把深度条件注释掉，预测会错在哪里；再把频率从 input.frequency 改为固定值。pixels 的每项是线性灰度近似，本周不做完整颜色管理；不要把 passed 当作 GPU 实际执行次数。

```js
const n = input.width * input.height;
const depth = new Array(n).fill(Infinity);
const pixels = new Array(n).fill(0);
let passed = 0;
for (const f of input.fragments) {
  if (input.depth === 'on' && f.z >= depth[f.i]) continue;
  depth[f.i] = f.z;
  const cell = (Math.floor(f.u * input.frequency)
              + Math.floor(f.v * input.frequency)) & 1;
  pixels[f.i] = cell ? 0.85 : 0.22;
  passed++;
}
return {width:input.width,height:input.height,pixels,passed,
        candidates:input.fragments.length};
```

### 如何判断结果

相机、UV/采样与可见性可能独立出错；一个“能运行”的图像也需要可验证的参考。

### 简化与边界

CPU 240×150 软件光栅，两个立方体、程序棋盘、无光照；近面相交整三角跳过，无 GPU 性能结论、mipmap 或完整裁剪。

## 预测、实验、解释

### 排查一张错误图，不同时改三个变量

先载入参考，再关闭深度并逆序提交。预测轮廓、UV 与遮挡分别是否改变。恢复一个变量后记录证据，提出能区分“投影错误”和“遮挡错误”的操作。

提示：若只交换顺序就改变重叠结果，优先验证深度状态；改变材质颜色不会修复错位轮廓。

### 把核心循环翻译成 OpenGL 数据流

说明 input.fragments、depth、pixels 分别对应哪些 GPU 管线概念。写出软件循环与真实 GPU 并行执行的两项差别，避免把这里的计数当作硬件统计。

提示：关注候选片段、深度缓冲、颜色缓冲；GPU 可提前深度测试。

### 1. 相机不动，只改棋盘频率，最应该保持什么？

1. 物体的投影轮廓
2. 所有像素颜色
3. CPU 运行时间必然相同

### 2. 深度测试关闭时，远物体一定显示在后面吗？

1. 一定

### 3. 屏幕重心权重直接插值 UV，在透视投影下通常怎样？

1. 总是精确
2. 一般需要倒数深度加权校正
3. 应完全禁止 UV 插值

答案：2。透视下需要 Σλu/d 除以 Σλ/d；正交或等深度等特殊情况可退化为线性插值。

</details>

### 4. 这页写入候选计数能说明实际 GPU 执行次数吗？

3. 只要分辨率一样就能

答案：2。硬件执行可能有并行、早期深度及优化；CPU 模型不能替代 GPU 测量。

1. 必然重建失败

## 常见误区

- 把投影、插值、采样和可见性混成一个“渲染问题”；应分开验证。
- 软件片段计数不是 GPU profiler，运行速度也不是 GPU 帧时间。
- 角点 UV 对了不代表中间的透视插值正确。
